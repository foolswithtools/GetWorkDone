# The stuck-item sweeper waited for its index, not the backoff columns its sweep uses, and the delivery worker read them too

Resolved in GWP#127, found while resolving PR #125's conflicts (#102 meeting #101), 2026-11-02. Not observed in the sandbox.

The sweeper waits for its schema before its first sweep (GWP#101, `apps/api/src/modules/database/schema-ready.ts`). It waited for `Item_status_updatedAt_idx`, which `20261031120000_waiting_role_and_archive` creates with the `waitingRole` column its filter then read. GWP#102 made the sweep also read and write `Item.sweepRetryAt` and `Item.sweepFailures` (the `findMany` filter in `ProcessService.stuckItems` and the backoff `UPDATE`), which only `20261102000000_sweep_backoff` adds. So an API started on a schema migrated up to the index but not the backoff passed the wait, and every sweep failed (`column "sweepRetryAt" does not exist`, logged at `error` as `stuck item sweep failed`) until the migration ran. The sandbox was not exposed: `deploy.yml` migrates before it rolls out a new image, and a fresh instance had neither the index nor the columns. A self-hoster who starts the new API before migrating was.

Fix: the sweeper waits for the column `Item.sweepRetryAt` (`STUCK_ITEM_COLUMN` in `apps/api/src/modules/process/stuck-item-sweeper.ts`), checked with a new `columnReady(db, table, column)` beside `schemaReady`. `sweep_backoff` adds both columns in one statement, and migrations apply in order, so once the column exists so do `sweepFailures` and `waitingRole` (and the index did, until `20261103180000_drop_item_status_updated_at_idx`, GWP#158, dropped it). The issue offered a new migration with an index on `sweepRetryAt` for the check to name instead; a column check needs no schema change and no index the sweep does not use, and the next column the sweep comes to need is one constant to change. `columnReady` reads `pg_catalog.pg_attribute` for the relation `to_regclass` names, not `information_schema.columns` as the issue suggested: that view lists only the columns of tables the role holds a privilege on (checked against Postgres 16 with a role holding no grant: the view found no `sweepRetryAt`, `pg_attribute` did), while the catalog, like `to_regclass`, needs none. The delivery worker, which waits for `Delivery`, shared the gap (found in the branch review): its `load` read the item with Prisma's `include`, so every `Item` column, `sweepRetryAt` among them. On such a schema each claim of a due delivery used an attempt and failed (`delivery attempt not recorded`), and after the third the row ended `failed` (`interrupted`) for an admin to retry. `load` now selects only the columns it sends, so it reads nothing a later migration adds to `Item`, and it keeps waiting for `Delivery` alone. The backlog gauge (`Delivery` count) and the session purge (`deleteMany` on the session and login tables and one raw `QuotaWindow` delete) read nothing added after their table, so they keep `schemaReady`.

Why no test caught it: the GWP#101 test starts the API on an empty database, where the index and the columns are both missing, and every other suite runs on a fully migrated one.

Regression tests:

- `apps/api/test/stuck-item-sweeper.integration.test.ts` (partition: integration), "with Item.waitingRole but not Item.sweepRetryAt it waits, logging its waiting line and no failed sweep, and sweeps once `prisma migrate deploy` adds the columns": a scratch database migrated and then put back to before `sweep_backoff` (its columns dropped and its `_prisma_migrations` row deleted), the API in production mode on it (its precondition checked the index until GWP#158 dropped it, and checks `Item.waitingRole` since). Before the fix the sweeper logged no waiting line and started at once.
  The same test seeds a due webhook delivery before the columns are dropped and expects it `delivered` on the first attempt before the migration; before the `load` fix it stayed `pending` with its attempt used.
- `apps/api/test/schema-ready.test.ts` (partition: unit), "columnReady (GWP#127)": the query reads `pg_attribute`, not `information_schema`, and table and column names it would have to escape are refused.
