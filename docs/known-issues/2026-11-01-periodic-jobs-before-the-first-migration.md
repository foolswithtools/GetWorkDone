# The periodic jobs logged an error every few seconds until a fresh instance's first migration

Resolved in GWP#101, found by the 2026-10-31 open-issue audit of `main` at a17458d. Observed on fresh `dev` deploys.

An instance's first deploy, or the first after a destroy, has no service for `migrate.sh` to copy, so the app stage starts the API on an empty database and the job migrates only afterwards (`docs/deploy/sandbox.md` "Migrations"). The delivery worker started polling at bootstrap and every `DELIVERY_POLL_MS`, and each run failed with Postgres's `relation "Delivery" does not exist` and logged `delivery run failed` at `error`: a line every 5 s until the migration landed. The session purge (`session purge failed`) and the stuck-item sweeper (GWP#55, `stuck item sweep failed`) failed the same way at startup. Each line is an OTel log record, counted against Loki's free tier, and the noise hid real errors.

Fix: one helper, `apps/api/src/modules/database/schema-ready.ts`. `schemaReady(db, table)` asks `to_regclass('public."<table>"')`; `waitForSchema` checks at once, then with backoff from the job's interval doubling up to 60 s, logs one `warn` (`<job> waiting for the database schema`) and one `info` (`<job> started`), and starts the job. The worker waits for `Delivery`, the purge for `QuotaWindow` (the newest table it deletes from), the sweeper for `Item_status_updatedAt_idx` (`to_regclass` resolves an index too; it is created with the `waitingRole` column the sweep filters on, so a check during `migrate deploy` cannot start the sweeper between the `Item` table and that column), and the backlog gauge (since GWP#127 the sweeper waits for the column `Item.sweepRetryAt` instead: [2026-11-02-sweeper-waited-for-the-index-not-the-backoff-columns.md](2026-11-02-sweeper-waited-for-the-index-not-the-backoff-columns.md)), which never logged but queried `Delivery` on every export, skips its exports until `Delivery` exists. A started job never checks again, so a table missing later still logs at `error`. A check Postgres refuses with `28P01` (the API's `getworkdone_app` role does not exist until the post-apply migrate task creates it, #57, so this is what a fresh sandbox instance sees first; the issue, written before #57 merged, expected only `relation ... does not exist`) or `3D000` is waited out like a missing table, under the same one `warn` (found in the second branch review). Any other failing check (the database unreachable) cannot tell, so the job starts at once after one `warn` and fails and reports as before; in particular the session purge keeps recording `status="error"` runs, which keep the `<env> telemetry heartbeat` series alive while the `database unreachable` rule names the cause (found in the branch review). The readiness check runs `SELECT 1` only and is unchanged.

Why no test caught it: every suite runs on a database the global setup or `createScratchDatabase` has migrated first, connected as its owner.

Regression tests:

- `apps/api/test/schema-ready.integration.test.ts` (partition: integration), "logs one warn per job and no error while the schema is missing, then starts every job once migrated and sends a due delivery", run twice: connected as the database owner, and as a role created only after the migration (28P01 until then), as in the sandbox. Before the fix the first saw `delivery run failed`, `session purge failed` and `stuck item sweep failed`, each with a `does not exist` error; with a helper that started the job on any failed check, the second saw the same three with an authentication error.
- `apps/api/test/delivery-worker.test.ts` (partition: unit): no claim while the table is absent, one `warn`, then one `info` and claims; a later claim error still logs `delivery run failed`.
- `apps/api/test/schema-ready.test.ts`, `apps/api/test/delivery-backlog.test.ts` and the GWP#101 cases in `session-purge.test.ts` and `stuck-item-sweeper.test.ts` (partition: unit).
