# A high advisory in effect, pinned by Prisma's config package, failed the audit gate

Resolved in GWP#172. GHSA-7589-6fvf-x4pw (high) was published on 2026-11-19. It is a ReDoS in `effect`'s `Schema.TemplateLiteral` compiled regex, affecting `effect` 3.22.0 and earlier, fixed in 3.22.1. The first `ci` run after it, on `main` at 726da4b (run 45056979836), failed its `audit` step: `pnpm audit --prod --audit-level=high` reported the path `apps__api>prisma>@prisma/config>effect`. Nothing in the code changed to cause it, and every `ci` run would have failed until the fix.

`apps/api` keeps `prisma` as a production dependency because the API image runs `prisma migrate deploy`. `prisma@7.10.1`'s `@prisma/config@7.10.1` pins `effect` at exactly `3.20.0`, and no Prisma 7.x release moves off it: `@prisma/config` 7.9.0 to 7.10.1 all pin `3.20.0`, and the only newer Prisma is an 8.0 release candidate. Runtime exposure was low. `effect` runs only inside the Prisma CLI, on config the repo supplies. `@prisma/client` reaches `@prisma/config` only through its peer dependency on `prisma`, the CLI. No file in `apps/api` or `packages/db` (source, build or generated client) imports `effect` or `@prisma/config`, so the API's request path never calls `Schema.TemplateLiteral`.

Fix, as README.md "Dependencies" says for a dependency that pins a vulnerable version exactly: a scoped override, `"@prisma/config>effect": "3.22.1"`, in `pnpm.overrides` in the root `package.json`, beside #51's `multer` one. `effect@3.22.1` was published on 2026-07-30, so `minimumReleaseAge` does not hold it back. Remove the override once a stable Prisma moves `effect` past 3.22.0.

Regression check: the `audit` gate (`pnpm audit --prod --audit-level=high`) exits 1 on `main` before the fix and 0 after it, and `pnpm why effect -r` lists only `effect@3.22.1`. The `integration`, `build`, `image` and `image-migrate` gates show that Prisma's CLI (`generate`, `--version`, `migrate deploy`) works on 3.22.1.
